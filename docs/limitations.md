# Limitations

- Only Manjaro package and systemd service discovery is implemented. System and user service scopes may be inaccessible, especially without a running user manager or system bus; unavailable means unknown. Desktop discovery is limited to known package names, a small set of fixed session-file paths and recognized current-process XDG hints. Missing or inaccessible session files may be unknown; the configured desktop and display-manager configuration are not determined. Hyprland or XFCE can be explicitly selected in a generated draft, but login managers and desktop settings are not migrated. Hardware discovery is partial: CPU model, visible EFI interface, PCI display/network devices and limited lsblk evidence only. USB, fstab, network settings, device identifiers and non-system mounts are not collected. EFI absence does not prove BIOS, and lsblk evidence is not sufficient to generate disk configuration. Networking is limited to interface category counts, nameserver categories, installed firewall packages and recognized network-manager service state. It does not retain addresses, interface names, hostname, DNS domains, VPN or Wi-Fi configuration, or determine effective firewall rules. Resolver symlinks outside known locations are treated as unknown. A fixed set of known configuration paths is checked for presence; file contents, alternate paths, and other users are not scanned. No private configuration or broader user-environment discovery is performed.
- The output includes an incomplete flake, modules, report and inventory, but is not a bootable or installable NixOS configuration. `validate` checks syntax and can optionally check package-attribute presence against a user-supplied Nixpkgs checkout. An explicitly opted-in module check evaluates the trusted project with placeholder hardware settings and checks system package names and NixOS assertions; it is not full system derivation evaluation. It does not prove package equivalence, service behavior, builds or boot behavior. Checkout revision metadata is not authenticated; matching `.git-revision` is not proof of identical content. The generated commit pin is not resolved and no lock is created automatically.
- Package mappings include curated entries and automatically inferred same-name, same-homepage catalog matches; service mappings are a small curated allowlist. They are not checked against a target revision during generation. Names can conceal differences in package features and behavior. Exact-name suggestions are not verified equivalents; user-reviewed mappings are not automatically checked for buildability or behavior. Service enablement does not transfer unit overrides, dependencies, secrets or application data; runtime-only and user services need manual review.
- The scanner and mapping database do not determine a target revision's license policy. A generated package can exist and pass partial checks but still cause a build to fail because it is unfree or disallowed by Nixpkgs policy. Nixify does not automatically permit unfree software.
- Foreign packages may be local, third-party, removed from sync repositories, or AUR; no specific provenance is inferred. Packages marked explicitly installed may have been selected by the original system image or installer.
- Baseline overlap is exact `pname` comparison against a minimal NixOS configuration evaluated from the specified checkout. It is not behavioral equivalence or a full source-to-target package mapping, and does not suppress generated packages. The target might use different modules or a different Nixpkgs revision.
- Separately, a small built-in set of source/attribute pairs is omitted from the direct package list only when a verified NixOS base or generated module supplies it, on x86_64 and the two specifically checked revisions. The generated report records these decisions; changing the provider, defaults, package override or target requires reassessment. Revision identifiers and bundled evidence are not authenticated against a checkout at generation time. Other target revisions retain direct packages, and many distribution defaults remain in the draft.
- Queries are separate snapshots; database inconsistencies are detected where possible, but changes that preserve set membership can go unnoticed. The process times out after 30 seconds and limits captured output to 4 MiB per stream.
- Nix package builds and live baseline evaluation may require access to the Nix daemon or other local Nix resources. This environment cannot access the daemon socket; `nix build` and `nix flake check` remain unverified here.

- Opt-in file-content inspection covers only two Hyprland settings and Docker live-restore. It omits unrecognized values, does not follow final symlinks or resolve includes, and does not migrate application data or user configuration files.

- Offline NixOS channel-catalog matches are name-based suggestions, not semantic or architecture verification. Their declared revision is supplied by the user and is not authenticated against the catalog.

- Optional `hardware-config` requires `nixos-generate-config` and captures its output for manual review. It does not configure the target disk or bootloader; source filesystem declarations, if explicitly requested, may be inappropriate for the destination.
